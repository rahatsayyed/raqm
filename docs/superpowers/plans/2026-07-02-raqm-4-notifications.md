# Raqm Plan 4: Notification System — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give Raqm a full local-notification layer: a styled transaction notification with a tap-to-detail deep link and an inline "Add note" action (T17/T18), daily/weekly/monthly spend-summary reminders gated on settings (T19–T22), and native cancellation of the raw SMS app's notification for bank messages (T23).

**Architecture:** All scheduling/response logic lives in one new module, `src/notifications/notifications.ts`, built on `expo-notifications`. A `navigationRef` (created once, wired into `NavigationContainer`) lets the notification-response listener navigate without prop-drilling. Summary notifications are local, device-scheduled reminders with static/generic bodies — `expo-notifications` cannot compute "today's total" at fire time, so the notification just says a summary is ready and tapping it opens the Dashboard, which shows live totals. T23 is pure Kotlin: extend the already-existing (but currently empty) `RaqmNotificationListenerService` to cancel matching bank-SMS notifications from known SMS apps.

**Tech Stack:** `expo-notifications` (SDK 56), `@react-navigation/native` (`createNavigationContainerRef`), Kotlin (`NotificationListenerService`), existing `src/db/database.ts` (`getSetting`, `updateTx`), Plan 3's `src/services/txIntelligence.ts` (`isDuplicateSms`) and `src/services/location.ts` (`getCurrentCoords`).

## Global Constraints

- Android-only. Do not add iOS-specific code paths beyond what the cross-platform `expo-notifications` API requires.
- All native (Kotlin/manifest) changes go inside `apps/raqm/modules/sms-reader/` — `android/` at the app root is gitignored and regenerated by CNG (`npx expo prebuild`/`expo run:android`), so nothing outside the local module survives a clean prebuild.
- `expo-notifications` API calls must match the SDK 56 docs exactly. Confirmed facts used throughout this plan (verified against `https://docs.expo.dev/versions/v56.0.0/sdk/notifications/` and the SDK 56 `Notifications.types.ts` source):
  - `SchedulableTriggerInputTypes` enum values: `DAILY = 'daily'`, `WEEKLY = 'weekly'`, `DATE = 'date'`, `TIME_INTERVAL = 'timeInterval'`.
  - `WeeklyTriggerInput.weekday` is **1–7 with `1` = Sunday** (not JS `Date.getDay()`'s 0-based convention).
  - `channelId` exists **only on trigger objects** (`DailyTriggerInput`, `WeeklyTriggerInput`, `DateTriggerInput`, etc.), never on `NotificationContentInput`. An immediate notification (`trigger: null`) cannot carry an explicit `channelId` — it uses the app's **default channel**, which is why this plan sets `defaultChannel` in the `expo-notifications` config plugin.
  - `NotificationContentInput.categoryIdentifier` (not `category`) attaches an action category to a notification.
  - `NotificationResponse` has top-level `actionIdentifier: string`, `userText?: string`, and `notification.request.content.data: Record<string, unknown>`.
  - `Notifications.DEFAULT_ACTION_IDENTIFIER` is the action identifier for a plain tap.
- Dark theme tokens (`Colors`, `Typography`, `Spacing`, `Radius` from `src/theme`) for any temporary/dev UI touched in this plan.
- Every task ends with `npx tsc --noEmit` (run from `apps/raqm/`) → expected: no errors.
- Do not run `git commit` unless the session controller explicitly states the user has approved commits. Otherwise leave changes in the working tree and skip the commit step.
- Copy contract signatures from `docs/superpowers/plans/2026-07-02-raqm-shared-interfaces.md` §4 verbatim; do not rename.
- This plan consumes Plan 2 (`TxRecord`, `useTxStore`, `updateTx`, `getTxById`, `getSetting`/`setSetting`) and Plan 3 (`isDuplicateSms`, `getCurrentCoords`, `countsTowardTotals`) only. It must not reference anything from Plans 5–7.

import * as Notifications from 'expo-notifications';
import type { NavigationContainerRef } from '@react-navigation/native';
import { getSetting, updateTx } from '../db/database';
import type { MainStackParamList } from '../navigation/types';

const TX_CHANNEL_ID = 'raqm-tx';
const TX_CATEGORY_ID = 'tx';
const ADD_NOTE_ACTION_ID = 'add-note';

const DAILY_SUMMARY_ID = 'raqm-daily-summary';
const WEEKLY_SUMMARY_ID = 'raqm-weekly-summary';
const MONTHLY_SUMMARY_ID = 'raqm-monthly-summary';

/**
 * Sets the foreground notification handler, requests POST_NOTIFICATIONS permission,
 * creates the Android notification channel used by every notification this app posts,
 * and registers the 'tx' action category with its inline text-input "Add note" action (T18).
 * Safe to call multiple times (idempotent on the native side).
 */
export async function initNotifications(): Promise<void> {
  Notifications.setNotificationHandler({
    handleNotification: async () => ({
      shouldShowBanner: true,
      shouldShowList: true,
      shouldPlaySound: true,
      shouldSetBadge: false,
    }),
  });

  await Notifications.requestPermissionsAsync();

  await Notifications.setNotificationChannelAsync(TX_CHANNEL_ID, {
    name: 'Transactions',
    importance: Notifications.AndroidImportance.HIGH,
    vibrationPattern: [0, 150, 100, 150],
    enableVibrate: true,
  });

  await Notifications.setNotificationCategoryAsync(TX_CATEGORY_ID, [
    {
      identifier: ADD_NOTE_ACTION_ID,
      buttonTitle: 'Add note',
      textInput: {
        placeholder: 'Add a note…',
        submitButtonTitle: 'Save',
      },
    },
  ]);
}

/**
 * Posts the styled transaction notification (T17, T23's JS-side half). Uses trigger: null
 * (immediate) so it lands on the app's default channel, which app.json's expo-notifications
 * plugin config points at 'raqm-tx'. Carries `data: { txId }` so attachNotificationHandlers
 * can deep-link on tap, and `categoryIdentifier: 'tx'` so the "Add note" action (T18) appears.
 */
export async function postTxNotification(txId: number, title: string, body: string): Promise<void> {
  await Notifications.scheduleNotificationAsync({
    content: {
      title,
      body,
      data: { txId },
      categoryIdentifier: TX_CATEGORY_ID,
    },
    trigger: null,
  });
}

/**
 * Posts a plain alert notification with no action category and no txId — used by Plan 5's
 * budget-threshold checks (B4/B5). Tapping it falls through to the "no txId" branch of
 * attachNotificationHandlers, which just opens the Dashboard.
 */
export async function postBudgetAlert(title: string, body: string): Promise<void> {
  await Notifications.scheduleNotificationAsync({
    content: {
      title,
      body,
      data: {},
    },
    trigger: null,
  });
}
```

/**
 * Wires up the single global notification-response listener.
 * - Tap with a txId in data (T17): navigate to TransactionDetail.
 * - Tap with no txId (summary notifications): navigate to the tab root (Dashboard is the
 *   first tab, so this lands the user there).
 * - 'add-note' action with typed text (T18): save the note directly to the DB without
 *   navigating or opening the app to the foreground.
 * Returns an unsubscribe function.
 */
export function attachNotificationHandlers(
  navRef: NavigationContainerRef<MainStackParamList>,
): () => void {
  const sub = Notifications.addNotificationResponseReceivedListener(response => {
    const data = response.notification.request.content.data as { txId?: number };

    if (response.actionIdentifier === ADD_NOTE_ACTION_ID) {
      const userText = response.userText;
      if (typeof data.txId === 'number' && userText && userText.trim().length > 0) {
        updateTx(data.txId, { notes: userText.trim() });
      }
      return;
    }

    if (response.actionIdentifier === Notifications.DEFAULT_ACTION_IDENTIFIER) {
      if (!navRef.isReady()) return;
      if (typeof data.txId === 'number') {
        navRef.navigate('TransactionDetail', { transactionId: data.txId });
      } else {
        navRef.navigate('Tabs');
      }
    }
  });

  return () => sub.remove();
}
```

Also exports `rescheduleSummaries` as an alias of the same function, and a **local, non-exported** `lastDayOfPeriod(startDay: number): Date` helper. **This helper is intentionally duplicated logic**: Plan 5 will later build a canonical `getMonthBounds(ref, startDay)` in `src/utils/period.ts`, but Plan 4 must not depend on Plan 5 (dependency rule in shared-interfaces §8), so this plan computes the same "last day of the custom-start-day month period" independently. Plan 5 does **not** replace or import this helper — the two implementations are separate and must each be kept correct on their own.

**Honest limitation (document this, don't try to work around it in this plan):** `expo-notifications` schedules content at *schedule time*, not at *fire time* — there is no way to make a locally-scheduled Android notification compute "today's total spend" right before it displays. So daily/weekly/monthly summary notifications carry a static, generic body ("Your daily spend summary is ready.") and tapping them opens the Dashboard, which then shows the real, live numbers. Additionally, `DAILY` and `WEEKLY` triggers are natively repeating on Android (the OS keeps re-firing them), but there is no repeating "last day of an N-day custom month" trigger type, so the monthly notification (T21) is scheduled as a single `DATE` trigger for the upcoming period-end. It will only be rescheduled for the *next* period the next time `scheduleSummaries()` runs (app launch, or a settings toggle in Plan 5) — if the app is never reopened between the fire date and the next period's end, the monthly reminder silently stops recurring until the app is next opened.

```ts
/**
 * Returns the last calendar day (at local midnight) of the custom month period that
 * contains "now", where a period runs from `startDay` of one month to the day before
 * `startDay` of the next month. E.g. startDay=1 → last day of the current calendar month.
 * startDay=15, today=Jul 20 → period is Jul 15–Aug 14, so this returns Aug 14.
 * startDay=15, today=Jul 10 → period is Jun 15–Jul 14, so this returns Jul 14.
 */
function lastDayOfPeriod(startDay: number): Date {
  const clampedStart = Math.min(Math.max(Math.trunc(startDay), 1), 28);
  const now = new Date();

  let periodStartMonth = now.getMonth();
  let periodStartYear = now.getFullYear();
  if (now.getDate() < clampedStart) {
    periodStartMonth -= 1;
    if (periodStartMonth < 0) {
      periodStartMonth = 11;
      periodStartYear -= 1;
    }
  }

  const nextPeriodStart = new Date(periodStartYear, periodStartMonth + 1, clampedStart);
  const lastDay = new Date(nextPeriodStart.getTime() - 24 * 60 * 60 * 1000);
  lastDay.setHours(0, 0, 0, 0);
  return lastDay;
}

async function cancelIfScheduled(identifier: string): Promise<void> {
  try {
    await Notifications.cancelScheduledNotificationAsync(identifier);
  } catch {
    // not scheduled — nothing to cancel
  }
}

/**
 * Reads notif_daily / notif_weekly / notif_monthly (T22) and month_start_day, cancels any
 * previously scheduled summary notifications by fixed identifier, then re-schedules the
 * ones that are enabled. Safe to call repeatedly (on app launch and whenever a Settings
 * toggle changes) — it is fully idempotent.
 */
export async function scheduleSummaries(): Promise<void> {
  await cancelIfScheduled(DAILY_SUMMARY_ID);
  await cancelIfScheduled(WEEKLY_SUMMARY_ID);
  await cancelIfScheduled(MONTHLY_SUMMARY_ID);

  const [dailyEnabled, weeklyEnabled, monthlyEnabled, monthStartDayRaw] = await Promise.all([
    getSetting('notif_daily'),
    getSetting('notif_weekly'),
    getSetting('notif_monthly'),
    getSetting('month_start_day'),
  ]);

  if ((dailyEnabled ?? '1') === '1') {
    await Notifications.scheduleNotificationAsync({
      identifier: DAILY_SUMMARY_ID,
      content: {
        title: 'Daily summary',
        body: 'Your daily spend summary is ready.',
        data: {},
      },
      trigger: {
        type: Notifications.SchedulableTriggerInputTypes.DAILY,
        hour: 21,
        minute: 0,
        channelId: TX_CHANNEL_ID,
      },
    });
  }

  if ((weeklyEnabled ?? '1') === '1') {
    await Notifications.scheduleNotificationAsync({
      identifier: WEEKLY_SUMMARY_ID,
      content: {
        title: 'Weekly summary',
        body: 'Your weekly spend summary is ready.',
        data: {},
      },
      trigger: {
        type: Notifications.SchedulableTriggerInputTypes.WEEKLY,
        weekday: 1, // 1 = Sunday per expo-notifications convention
        hour: 20,
        minute: 0,
        channelId: TX_CHANNEL_ID,
      },
    });
  }

  if ((monthlyEnabled ?? '1') === '1') {
    const startDay = Number(monthStartDayRaw ?? '1');
    const fireDate = lastDayOfPeriod(startDay);
    fireDate.setHours(20, 0, 0, 0);

    if (fireDate.getTime() > Date.now()) {
      await Notifications.scheduleNotificationAsync({
        identifier: MONTHLY_SUMMARY_ID,
        content: {
          title: 'Monthly summary',
          body: 'Your monthly spend summary is ready.',
          data: {},
        },
        trigger: {
          type: Notifications.SchedulableTriggerInputTypes.DATE,
          date: fireDate,
          channelId: TX_CHANNEL_ID,
        },
      });
    }
  }
}

/**
 * Alias so Plan 5's Settings screen can call `rescheduleSummaries()` after toggling
 * notif_daily/notif_weekly/notif_monthly or changing month_start_day — same function,
 * named for readability at the call site.
 */
export const rescheduleSummaries = scheduleSummaries;
```

**Files:**
- Modify: `apps/raqm/modules/sms-reader/android/src/main/java/expo/modules/smsreader/RaqmNotificationListenerService.kt`

**Interfaces:**

- Produces: no new JS-visible API. The service runs automatically once notification listener access is granted (via the existing `SmsReader.openNotificationListenerSettings()` JS call, already wired into onboarding).

**Honest limitations to keep in mind while implementing (do not try to fix these in this task):**
1. Cancellation only works while the user has granted "Notification access" to Raqm in Android system settings (existing onboarding flow via `openNotificationListenerSettings`) — if access is revoked, the raw SMS app notification will not be cancelled.
2. This only cancels the notification from the phone's default SMS/Messages app. It does **not** touch `SmsBroadcastReceiver.kt`'s own separately-posted "New bank message" native notification (channel `raqm_transactions`), which fires independently of whether the JS/React Native side is running. When the app process is fully killed, the user will see that generic native notification (not the rich, merchant/amount-styled one from Task 4 — Kotlin has no access to the JS bank-SMS parser). The rich, styled notification only appears when the JS live listener is alive to run it. This is an accepted limitation of the v0 architecture, not something this task should attempt to resolve.

- [ ] **Step 1: Implement `onNotificationPosted` cancellation logic**

Replace the full contents of `apps/raqm/modules/sms-reader/android/src/main/java/expo/modules/smsreader/RaqmNotificationListenerService.kt` with:

```kotlin
package expo.modules.smsreader

import android.app.Notification
import android.service.notification.NotificationListenerService
import android.service.notification.StatusBarNotification

private val KNOWN_SMS_PACKAGES = setOf(
  "com.google.android.apps.messaging",
  "com.samsung.android.messaging",
  "com.android.mms",
)

private val SENDER_CODE_PATTERN = Regex("\\b[A-Z]{2}-[A-Z0-9]{4,}\\b")

class RaqmNotificationListenerService : NotificationListenerService() {

  override fun onNotificationPosted(sbn: StatusBarNotification) {
    super.onNotificationPosted(sbn)

    if (sbn.packageName !in KNOWN_SMS_PACKAGES) return

    val extras = sbn.notification.extras
    val title = extras.getCharSequence(Notification.EXTRA_TITLE)?.toString() ?: ""
    val text = extras.getCharSequence(Notification.EXTRA_TEXT)?.toString() ?: ""

    if (looksLikeBankNotification(title, text)) {
      cancelNotification(sbn.key)
    }
  }

  private fun looksLikeBankNotification(title: String, text: String): Boolean {
    val combined = "$title $text"
    val lower = combined.lowercase()

    val hasBankKeyword = lower.contains("debited") ||
      lower.contains("credited") ||
      lower.contains("a/c") ||
      lower.contains("acct") ||
      lower.contains("upi") ||
      lower.contains("neft") ||
      lower.contains("imps")

    val hasSenderCodePattern = SENDER_CODE_PATTERN.containsMatchIn(combined)

    return hasBankKeyword || hasSenderCodePattern
  }
}
```

No manifest changes are needed — `AndroidManifest.xml` already declares the service with the correct permission and intent-filter (verified in the "Read first" section above).
